### 그레이스풀 셧다운
- 서버를 종료할 때 진행 중인 작업을 완료하고 안전하게 종료하는 방식
- 진행 중인 요청을 완료 ➡️ 새 요청 거부 ➡️ 리소스 정리 ➡️ 종료
- 반면 강제 종료는 즉시 프로세스를 종료 ➡️ 진행 중인 요청 손실 ➡️ 데이터 유실 가능
- 데이터 유실 방지: 처리 중인 트랜잭션이 완료될 시간 확보
- 사용자 경험: 진행 중인 요청이 갑자기 끊기지 않음
- 리소스 정리: DB 커넥션, 파일 핸들 등을 깔끔하게 정리
- 무중단 배포: 로드밸런서가 트래픽을 다른 서버로 옮길 시간 확보
- Kubernetes의 경우 Pod 종료 시 자동으로 SIGTERM을 보내고 기본 30초의 유예 시간(grace period)을 준다. 이 시간 안에 그레이스풀 셧다운을 완료해야 한다.
- Docker도 `docker stop` 명령어를 쓰면 SIGTERM을 보내고 10초를 기다린 후 SIGKILL로 강제 종료한다.
- CI/CD 파이프라인에서 무중단 배포를 구현할 때 필수적으로 고려해야한다.

<br>

### 그레이스풀 셧다운의 과정
- 1️⃣ 종료 신호 수신(SIGTERM)
  - OS나 컨테이너가 종료 신호 전송

- 2️⃣ 새 요청 거부
  - 헬스 체크를 Unhealthy로 변경
  - 로드밸런서가 트래픽을 다른 서버로 보냄
  - 새로운 요청 받지 않음

- 3️⃣ 진행 중인 요청 완료 대기
  - 현재 처리 중인 HTTP 요청 완료까지 대기
  - 타임 아웃 설정

- 4️⃣ 리소스 정리
  - DB 커넥션 풀 정리
  - 파일 핸들 닫기
  - 캐시 플러시
  - 로그 기록

- 5️⃣ 프로세스 종료
