### selectivity
- 선택도
- 테이블의 특정 열을 기준으로 해당 열의 `WHERE` 절 조건문에 따라 선택되는 데이터 비율
- 해당 열에 중복되는 데이터가 많다면 선택도가 높다. 👉 대량의 데이터가 선택될 것이다.
- 낮은 선택도를 가지는 열은 데이터를 조회하는 SQL문에서 원하는 데이터를 빨리 찾기 위한 인덱스 열을 생성할 때 주요 고려대상이다.
- `선택도 = 선택한 데이터 건수 / 전체 데이터 건수`
- 중복이 제거된 데이터의 건수를 활용하여 선택도를 일반화한다. 👉 선택하는 조건절의 데이터 건수를 매번 계산할 수 없고 데이터의 삭제와 수정, 삽입이 수시로 발생하기 때문이다.
- `변형된 선택도 = 1 / DISTINCT(COUNT 열명)`
- 1️⃣ 전체 데이터 건수 구하기
  - `SELECT COUNT(*) FROM {테이블};`
- 2️⃣ 해당 데이터에서 중복을 제외한 개수 구하기
  - `SELECT COUNT(DISTINCT {필드}) FROM {테이블};`
- 3️⃣ 열의 선택도 구하기
  - `SELECT 1 / COUNT(DISTINCT {필드}) FROM {테이블};`

### cardinality
- 하나의 데이터 유형으로 정의되는 데이터 행의 개수
- 전체 데이터에 접근한 뒤 출력될 것이라 예상되는 데이터 건수
- 실무에서는 전체 행에 대한 특정 열의 중복 수치를 나타내는 지표로 자주 활용한다.
- `카디널리티 = 전체 데이터 건수 * 해당 열의 선택도`
- 열별 선택도를 알고 있다면 카디널리티를 정량적 수치로 산출할 수 있다.
- 특정 열에 중복된 값이 많으면 카디널리티가 낮다. 👉 해당 열을 조회하면 상당수의 데이터를 거르지 못한 채 대량의 데이터가 출력될 것을 예측할 수 있다.
- 중복도가 높으면 카디널리티가 낮고 중복도가 낮으면 카디널리티가 높다.
- ex) 주민등록번호는 카디널리티가 높다.
- ex) 성별은 카디널리티가 낮다.

### hint
- 힌트
- 데이터를 빨리 찾을 수 있게 추가 정보를 전달한다.
- `SELECT {필드} FROM {테이블} /*! USE INDEX ({인덱스명}) */ WHERE {조건};`
- `SELECT {필드} FROM {테이블} USE INDEX {(인덱스명)} WHERE {조건};`
- 실무에서 자주 사용하는 힌트
  - ⭐ **STRAIGHT_JOIN** FROM절에 작성된 테이블 순으로 조인을 유도하는 힌트 
  - ⭐ **USE INDEX** 특정 인덱스를 사용하도록 유도하는 힌트 
  - **FORCE INDEX** 특정 인덱스를 사용하도록 강하게 유도하는 힌트
  - **IGNORE INDEX** 특정 인덱스를 사용하지 못하도록 유도하는 힌트
- 옵티마이저는 비효율적이라고 예측하면 사용자가 작성한 힌트를 무시하기도 한다.
- MySQL과 MariaDB에서는 작성한 힌트의 오브젝트가 존재하지 않으면 에러가 발생한다. 👉 운영 서비스에서 장애로 이어진다.

<br>

### collation
- 특정 문자셋으로 데이터베이스에 저장된 값을 비교하거나 정렬하는 작업의 규칙
- **utf9_bin**은 A B a b순이다.
- **utf8_general_ci**는 A a B b순이다.
- 콜레이션은 데이터베이스 단위, 테이블 단위, 열 단위까지 설정할 수 있다.

<br>

### 통계정보
- 옵티마이저는 통계정보에 기반을 두고 SQL문의 실행 계획을 수립
- 통계정보는 DBA가 맡을 역할이다.
- 쿼리를 수행하는 역할자 또한 통계정보가 현재 최신으로 관리되는지, 오래된 통계정보 때문에 SQL문이 엉뚱한 방향으로 수행되지는 않는지를 확인할 수 있다.
- MySQL은 시스템 변수를 통해 활용할 통계정보의 수준을 정의할 수 있다.
- 테이블 통계정보와 인덱스 통계정보, 선택적인 열 통계정보를 토대로 어떤 인덱스를 활용해 데이터에 액세스할 것인지, 어떤 테이블을 드라이빙 테이블로 선택할지 등을 결정한다. 👉 통계정보의 최신성 유지 및 관리가 매우 중요하다 !

<br>

### histogram
- 히스토그램
- 테이블의 열값이 어떻게 분포되어 있는지를 확인하는 통계정보
- 옵티마이저가 실행 계획을 최적화하고자 참고하는 정보
- 잘못된 히스토그램 정보가 있다면 잘못된 실행계획으로 SQL문이 수행될 수 있다.
- 특정 열값들의 통계정보가 히스토그램으로 수집되지 않았다면, 중복이 제거된 열값의 개수(`COUNT(DISTINCT 열명)`)로 대략적인 열값의 분포를 예측하고 실행 계획을 수립한다.
- MySQL에서 내부적으로 열의 분포를 저장할 때는 **height balanced histogram** 방식을 사용한다.
- 저장된 데이터값의 종류가 수만 개 이상이므로 이 데이터 값들을 그룹화하고, 정해진 bucket만큼 분리해서 열의 통계정보 데이터를 저장
- 실제 데이터베이스에서 관리하는 히스토그램의 버킷은 최댓값을 보관한다.
- `ANALYZE TABLE {테이블} UPDATE HISTOGRAM ON {열명};`
- `SELECT * FROM INFORMATION_SCHEMA.COLUMN_STATISTICS;`를 통해서 결과를 확인한다.
